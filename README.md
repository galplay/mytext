# 在线刷题网站 DS刷题（后端版）
# harness：Qoder   model：Qwen3.8-flash

2026 网页部招新考核的个人作品。一个**有后端，有背景（我），有数据库**的在线刷题网站：
两个题库、16 个章节页、深色模式、断点续刷、错题清零、收藏笔记、好友排行、
题目纠错反馈，还有一个可以拖动、会说话、答对天降米饭、答错当场宕机的看板娘。
「在线刷题」的**服务器形态**：
页面外观和交互与游客模式完全相同，但账号、作答记录、收藏、笔记、好友、排行榜、PK 全部保存在服务器上的 SQLite 数据库里——**换台电脑、换个浏览器登录同一
账号，就能接着刷**。不登录的游客依旧可用（数据只存本机浏览器）。

## 二、内容设计思路——我是怎么拆解并实现这些需求的

### 1. 先定架构，再写页面

考核一开局我先做了三个决定，后面所有功能都长在这三块地基上：

**决定一：题库数据与页面彻底分离，构建时生成。**
交付要求「把 Markdown 转成你自己的格式是工作的一部分」，同时红线是「不许改题库源文件」。
我的方案是写一个构建脚本 `tools/build.mjs`：读取原始的两份题库 md（`Web题库.md` / `Java题库.md`，
**一个字节都没动过**），解析成结构化数据，输出 `data/web.js` 和 `data/java.js` 两个题数据模块；
题目勘误**不改源文件、也不直接改产物**，而是在脚本里的 `FIXES` 表登记，构建时统一应用——
这样「原始数据 → 转换规则 → 产物」三者可复现，任何人重跑一次 build 都能得到同样的站点。
为什么用 `.js` 而不是 `.json` 或接口拉取：题目数据和页面代码同源加载，`<script src>` 一条请求到位，
不用等接口往返；而且就算服务器没跑起来、直接双击 `index.html`，题目照样能全部显示
（`file://` 下浏览器禁止 `fetch` 本地 JSON，`<script src>` 不受此限制）——后端版顺手保住了这条退路。

**决定二：所有数据读写只走一层「数据门面」`js/store.js`。**
进度、对错记录、收藏、笔记、用时全部收敛到这一个文件里，页面只认统一接口，不认存储本身：
登录用户走服务器的 SQLite，游客自动退回本机 localStorage。答题引擎 `quiz.js` 完全不知道数据存在哪，
`quiz.js`、`wrongquiz.js`、`profile.js`、`rank.js` 这些页面脚本一行都不用为「换数据源」改写——
这就是后文「一个前端，两种数据源」能成立的原因。

**决定三：16 个章节页由一份模板生成，不在 16 个文件里复制粘贴。**
`tools/template-chapter.html` 是唯一的章节页模板，`build.mjs` 按「题库 id + 章节号」批量生成。
后来改做题页背景、改看板娘挂载方式，都是改模板重跑一次脚本，16 页同步更新——
对应评分标准里那句「改一条规则要动几个地方？」

### 2. 答题引擎：把「底线」当设计约束

「同一道题重复点几次提交，成绩不能跟着变」这条底线，我的实现是两道保险：
提交按钮按下后该题立即进入已判分状态（锁），且判分结果写入的是
「题号 → 对错」快照而不是累加计数器——就算用户用后退、刷新、连点等方式绕过来，
重放提交也只是覆写同一条记录，正确率永远等于对题数除以总题数。

### 3. 看板娘：一张绿幕图的浏览器端流水线

看板娘素材是 AI 生成的绿幕立绘，浏览器里没法用 PS 抠图，所以 `js/mascot.js` 里
我让她**运行时自己抠图**：把图画进离屏 canvas，逐像素算「绿色超出红蓝的程度」，
超出多的全透明、超出一点的低 alpha 羽化并压掉绿溢；同时统计不透明像素的包围盒，
用来把构图略有差异的多张立绘（睁眼/眯眼/接盆/干饭/躺平）对齐到同一个脚底锚点。
眨眼不整图切换（会跳），而是把闭眼图的眼部圆形区域羽化后只贴眼睛。
动画统一走一个 requestAnimationFrame 循环：摇摆、呼吸、果冻压弹（阻尼振荡）、
天降米饭序列、宕机序列，全部以脚底中心为支点做变换，所以压扁拉伸时她不会离开地面。
交互上做了点击/拖动区分：6px 位移阈值 + 300ms 点击抑制窗，
拖动用 Pointer Events + 视口 clamp，手机上一指拖走不触发页面滚动（`touch-action: none`）。

### 4. 背景体系：三层纯 CSS，没有一张全屏大图

- **全站氛围底**（body）：白天是米白纸感——一条 240px 的内嵌 SVG `feTurbulence` 噪点
  平铺叠加暖色渐变，纸纹不到 1KB；夜晚是星空黑——14 层互质尺寸的 `radial-gradient`
  星点叠深蓝三段渐变，全部 `background-attachment: fixed`，滚动时星星不动。
- **做题页海报**（`.page--quiz`）：窄屏用「海报 + 半透明页面色罩」，氛围透出但不吵字；
- **≥1100px 电脑档**：海报按原比例占满屏高、贴右站好，题栏整体左移半个海报宽
  （`translateX(-34vh)`）落在左边空白正中——一张完整海报 + 一屏看完的题卡。

海报压到 800×1200 / 177KB 才入库（过程见第三节）。UI 是计入评分的，
但我不想为了好看把首屏压进几百 KB 的图里，所以背景体系的原则是：**氛围尽量用可平铺的
小纹理和渐变解决，大图的地位只留给做题页那一张，并且必须完整显示。**

## 三、AI 使用情况——做了什么、哪里错过、我怎么发现的

### AI 主要帮我的三件事

1. **写代码和注释**：全部 JS/CSS 由 AI 按我的方案产出，我要求全中文注释、ES5 风格，
   保证我能逐行讲解（这是我给自己定的答辩底线）。
2. **批量操作**：图片改名入库、16 个章节页重建、静态版/后端版两套目录同步拷贝，这类机械劳动全部交给它。
3. **浏览器自动化实测**：用 AI 操作浏览器截图、量元素坐标、模拟点击拖动——下面那些「发现不对」，多数是靠这个抓出来的。

### 但视觉判断是我的，翻车记录如下（按题面要求，一条不删）

- **章节封面第一次排错了顺序。** AI 按文件名顺序把横版封面分给 16 个章节，我打开首页一看，
  色系完全乱跳。发现方式很朴素：自己盯着看了一秒。重做的方案是我定的：
  先量每张图的主色调，按颜色连续分块排布，同名覆盖。
- **看板娘的宽屏定位，AI 最初算错了几何。** 它给了两档媒体查询（≥1101 和 ≥1341），
  按视口宽度算位置。我在内置浏览器（视口只有 510px）里没法直接验，就用同源 iframe
  注入一个 1400×900 的模拟视口量坐标，才发现：容器 `max-width` 封顶 1040px，
  所以 ≥1341 那一档永远多余，而 1341~1500 区间娘的位置会和正文打架。
  重算几何后统一成一档规则，一次算定。
- **海报第一次压完 341KB 不达标。** AI 按常规思路压 900px/质量80，体积没下来。
  看图发现是纸纹噪点特别吃 JPEG 体积，降到 800px/质量62 才压到 177KB——
  这个取舍（噪点图要更狠的压缩）是我先看到文件体积才发现的。
- **压海报的脚本第一次直接跑炸了。** 输出路径带中文目录时 PowerShell 编码出问题，
  AI 改成先输出到 ASCII 临时路径、再用另一条命令拷进中文目录，才稳。
- **「按 Ctrl+- 缩放来模拟宽屏」是个不可行的验证方案。** AI 连按 6 次后实测
  CSS 视口纹丝不动（内置视口固定 510px），`window.open` 弹窗也被拦截。
  发现方式是直接读 `window.innerWidth` 验证假设。换掉方案才有上面那条 iframe 实测。
- **合成事件的测试结果要甄别。** 测拖动时出现过「起点 y=905」这类怪数值，
  是页面滚动恢复和事件时序叠加的测试环境噪音，不是代码 bug——
  滚回顶部重测，坐标精确跟随、边界正确 clamp 之后才敢下结论。
  **错题本中的题写了未提交后，被移除错题本**  ai把 || 写成了 + 。

小结：AI 写代码快，但它「没有眼睛」这句我体会极深。上面每一条错误方案，
**发现渠道都不是 AI 自己，而是我打开页面看了、量了、或者拿数据验证了它的假设**。
我的分工是：方向、审美、几何、取舍由我定；实现、批量、实测脚本交给它。

## 四、运行方式


**依赖**：Node.js 22.13 或以上（用到内置的 `node:sqlite` 模块，本机 Node 24.16 验证通过）。
**不需要 `npm install`**——没有用任何第三方包，只用到 Node 自带的 `http` / `sqlite` / `crypto`。

```bash
# 在项目根目录（本文件夹）执行：
node server/server.js
# 或
npm start

# 然后浏览器打开：
http://localhost:3000
```

- 换成其他端口：`PORT=8080 node server/server.js`（Windows PowerShell 用 `$env:PORT=8080; node server/server.js`）
- 数据库文件 `server/data.db` **首次启动时自动创建**（建表语句是 `IF NOT EXISTS`，不会清数据）
- **Linux 部署**：把整个文件夹拷过去，在项目根目录 `node server/server.js` 即可；
  想常驻可以用 `nohup node server/server.js &` 或配 systemd。放行端口后访问 `http://服务器IP:端口`
- 直接双击 `index.html`（file:// 方式）时只有游客模式，页面顶部会自动提示去跑服务器——
  这是预期行为，不是报错

  
## 两种数据源，一个前端：游客走本机，登录走服务器

页面代码（`js/quiz.js`、`js/home.js`…）完全不知道自己工作在哪种模式，
全部数据读写都走 `js/store.js` 这一层"数据门面"：

| | 游客（未登录） | 登录用户 |
|---|---|---|
| 数据存哪 | 本机浏览器 localStorage | 服务器 SQLite（本机内存留一份镜像） |
| 键名示例 | `quiz.u.guest.progress.web.web-3` | 服务器 `records` / `chapters` 表 |
| 换电脑 | 数据不跟随 | 登录后自动恢复 |

注册或登录时，如果本机存有游客数据，会弹窗询问**是否一键导入账号**——
导入成功后本机游客数据清空，之后都走服务器。

### 增量同步

作答时不可能每次把整章传上去。`js/store.js` 里为每一章留了一份"快照"
（题号 → 这条作答的标准串），保存时逐题对比：

- 新题出现 / 内容变了 → 收进 `changes` 发出去；
- 题被删了（重做错题）→ 发 `{ qid, remove: true }`；
- 全部没变 → 一个请求都不发。

先按本地规则把界面和快照**乐观更新**，请求失败就把快照**回滚**，下次保存会重发一遍，
不会丢数据。服务器返回它算好的累计用时 `acc` 后，再用服务器的值覆盖本地。

**累计用时规则（前后端一致）**：距上次保存 10 分钟以内的间隔才计入 `acc`，
超过视为挂机只重新计时——所以排行榜上的"用时"是真实作答时间。

## 数据库（server/db.js，8 张表）

| 表 | 存什么 |
|---|---|
| `users` | 账号：用户名、昵称、盐、密码散列、头像(JSON)、签名、注册时间 |
| `sessions` | 登录会话：token → 用户名（浏览器存 token，服务器凭它认人） |
| `friends` | 好友关系（双向各存一行） |
| `records` | 逐题作答：草稿(ok=NULL) / 答对(ok=1) / 答错(ok=0) |
| `stars` | 题目收藏 |
| `notes` | 题目笔记 |
| `chapters` | 每章进度：断点 `pos`、交卷 `done`、累计用时 `acc`、上次保存时间 `last_ts` |
| `feedback` | 题目纠错反馈（维护日志）：题目标识、类型、正文、提交人（游客为 NULL）、处理状态 |

## 接口一览（server/server.js，共 20 条）

| 方法 路径 | 作用 |
|---|---|
| `POST /api/register` | 注册 `{name, pass, nick?}` → `{token, user}` |
| `POST /api/login` | 登录同名参数，返回新 token |
| `POST /api/logout` | 注销当前 token |
| `GET /api/me` | 当前用户信息 + 战绩汇总 |
| `GET /api/my-data` | 一次性拉全部学习数据（记录/收藏/笔记/章节） |
| `POST /api/sync` | 保存一章的增量改动 `{bank, chapter, pos?, done?, changes[]}` |
| `POST /api/star` | 收藏 / 取消收藏 `{qid, on}` |
| `POST /api/note` | 保存单题笔记 `{qid, text}` |
| `POST /api/reset-chapter` | 清空一章作答（收藏笔记保留） |
| `POST /api/import` | 游客数据一次性导入 |
| `POST /api/profile` | 改昵称 / 签名 / 头像 |
| `POST /api/friend/add` `remove` | 加 / 删好友 `{name}` |
| `GET /api/leaderboard` | 全站排行榜数据 |
| `GET /api/stats` | 注册人数（首页展示） |
| `POST /api/clear-my-data` | 清空自己的全部学习数据 |
| `POST /api/feedback` | 提交题目纠错 `{qid, bank, chapter, qNo, type, text}`（游客也可提交） |
| `GET /api/feedback` | 维护日志列表（公开；登录时每条带 `mine` 标记） |
| `POST /api/feedback/done` | 标记 / 取消「已处理」`{id, done}`（需登录） |
| `POST /api/feedback/remove` | 删除反馈 `{id}`（仅限本人登录时提交的） |

认证方式：请求头 `Authorization: Bearer <token>`；未登录访问受保护接口统一返回
`401 {error:'请先登录'}`，前端收到 401 会自动退回游客身份并提示重新登录。

## 五、如果再给我 1 小时，最想完善什么？为什么？

按「对用户的实际价值 ÷ 所需时间」排序：

1. **看板娘位置持久化 + 双击归位**（约 15 分钟）。她的可拖动是我自己很喜欢的功能，
   但现在刷新后位置会丢、拖到角落的素人也找不回来（答辩前我自己就「找不到她」过一回）。
   用 `store.js` 存一个坐标、双击回到默认位，小改动、体验闭环。
2. **宽屏真机回归清单跑一遍**（约 20 分钟）。我的内置测试视口只有 510px，
